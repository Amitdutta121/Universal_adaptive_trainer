Four ways to build a taxonomy by hand

All four end in the same place: the builder assembles one taxonomy document and sends it through the existing POST /curriculum/versions. So what differs is only how a professor types and rearranges a Topic → Subtopic tree. Variants A–C are live enough to click and type into; D is static.

Shared across every variant, and shown once at the bottom: a draft that autosaves, a rejection banner using the backend's own message, the "this replaces the live taxonomy" confirm, and a read-only JSON preview. Limits shown (300 / 2000) are the ones /curriculum/document-guide would supply.

Variant A

Inline outline editor

The version-detail tree, but every name is an input. One column, everything visible, no modes.

Good for
  • Smallest build; near-copy of curriculum-tree.tsx
  • Reads like the page it will become
  • Best on a phone or narrow window
Weak at
  • Long taxonomies become a long scroll
  • Moving a subtopic to another topic is cut/paste, not a drag
Variant B

Topic list + detail pane

Topics down the left, the selected topic's description and subtopic table on the right. Same shape as a settings screen.

Good for
  • Scales to 15+ topics; only one topic's inputs on screen at once
  • Left rail doubles as an outline and a reorder list
  • Table makes many subtopics fast to tab through
Weak at
  • Can't see the whole tree in one glance
  • Two panes need a stacked layout under ~760px
Variant C

Type an outline, see the tree

No form at all: one line per item, indent for subtopics, — before an optional description. The right side is the parsed result. This is the paste-from-notes path made first-class.

Good for
  • Fastest way to enter 40 subtopics from a syllabus
  • Paste a bullet list straight from a doc
  • Reorder by moving lines
Weak at
  • Introduces a second input format the app must define and parse
  • Least discoverable; a professor has to learn the syntax
  • Long descriptions get awkward on one line
Variant D · static

Board: topics as columns

Each topic is a column, each subtopic a card you drag between columns. Best when the job is restructuring rather than typing.

Good for
  • Moving a subtopic to another topic is one drag
  • Grouping and regrouping feels natural
Weak at
  • Worst for typing many items; each card is a small form
  • 8+ topics means horizontal scrolling
  • Needs dnd-kit cross-container drag plus a keyboard alternative: the heaviest build
Shared by all four

Rejection, confirm, and JSON preview

These do not depend on which editor wins.

Replace the live taxonomy?

Saving creates a new version and makes it the one questions and coverage use. The current one, Introductory Python (v3, 4 topics · 11 subtopics), becomes Replaced.

Questions and student measurements already recorded stay attached to the old version.
