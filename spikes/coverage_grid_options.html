Four ways to show the coverage grid

The professor's question is always the same: what should I generate next? All four layouts below answer it from the same numbers and support the same action — tick the gaps you want filled, then send them to the generator. They differ in what they put first.

Every number on this page is invented. Nothing here reads the real question bank, and no button does anything except tick. Pick a direction and it gets wired to /api/coverage.

What all four have in common

The two axes
Subtopic down the side, difficulty across the top — because that is exactly the pair the training engine asks for when it picks a student's next question.
The target
Three questions per box. A box holding one question shows a student the same question twice in a row, so three is the smallest number that rotates.
The action
Tick any box that needs filling. A running total at the bottom says how many questions that adds up to, then one button hands the list to the generator.
0 None yet — a student can be sent here and find nothing 2 Needs more — works, but repeats 5 Good — enough to rotate

Colour is never the only signal: the count is printed in every box, and the three states also differ by border — dashed, thin solid, filled. That keeps it readable in greyscale, on a projector, and for colour-blind readers.

Option A

The wall chart

One box per subtopic and difficulty, coloured and counted. The most literal picture of the curriculum — you see the whole shape of the bank at once, and the red patches are the work.

Costs

Option B

Three slots to fill

Same grid, but each box is drawn as three sockets — filled for a question you have, hollow for one you still need. Nobody has to know that three is the target or remember what amber means; the empty circles say it.

Reads well
Explains itself with no legend and no training. "Fill the empty circles" is the whole instruction, and the shape carries the meaning even printed in black and white.
Costs
Hides depth above three — a subtopic with forty easy questions looks the same as one with three unless you read the +n. Fine for filling gaps, wrong for spotting over-generation.

Option C

The worklist

No grid at all. Just the gaps, worst first, each one a line you can act on. This is the layout that treats coverage as a to-do list rather than a report — you never have to find the red squares, because nothing else is on screen.

Reads well
Zero interpretation required, and it scales to any taxonomy size — a hundred subtopics still produce a list you work down. Best for someone who just wants to be told what to do.
Costs
No overview. You cannot see that the bank is healthy, cannot spot a whole topic that was never written for, and there is no sense of progress from the list shrinking.

Option D

Topic by topic

The grid folded into one card per topic, each with a one-glance health bar. Closed, the page is six lines and you can see which topic is in trouble. Open, it is Option A for that topic only. This is the version that survives a sixty-subtopic curriculum.

What I'd suggest, and what I need from you

B for the boxes, C underneath it. The socket idea explains the rule without a legend, which is what "easy for anyone" really costs; the worklist below it means nobody has to hunt for the red. Option D's topic folding is worth adding later, when a real taxonomy makes the page too long — it is a change to A/B, not a replacement for them.

Four things would change the design, so tell me before I build:

  • How big is a real taxonomy? Seven subtopics and sixty subtopics want different layouts. This is the single biggest factor.
  • Is three per box actually your target? It is the code's current minimum. If you want ten, the socket idea in Option B stops working and the counts in A win.
  • Should ticking a box really queue generation? The generator picks its own subtopic from a chunk you choose — it cannot be ordered to write for a named subtopic. So "Generate these" honestly means "find me chunks that teach these", which is a real feature, not a button.
  • Is this for the professor, or for a paper? A figure wants one static grid, no interaction, and print-safe colour. A working page wants all of the above.
