Adaptive Trainer Database Map

Everything the app remembers lives in one SQLite file (data/adaptive_trainer.db). The tables fall into six areas. A professor fills the first five; students fill the last one. Read the map, then follow one question from book to student.

The life of one question

The order things happen in the app, and the tables each step writes to.

  1. A professor creates a course

    They pick a subject (Intro Python, Physics, ML & LLMs…) and the question types the course will use.

    courses

  2. They upload a textbook

    The book is split into chapters and sections. Each section's text gets an embedding for search.

    booksbook_chaptersbook_sectionssection_embeddings

  3. They build a taxonomy

    Topics and subtopics, by hand, from JSON, or drafted by the AI. Each version is kept.

    curriculum_versionstopicssubtopicssubtopic_evidence

  4. The AI writes a question

    From one section, one type, one difficulty. It is checked (does the answer key hold up?) and retried if a check fails.

    questionsquestion_subtopics

  5. Four AI judges score it

    Issues, subtopic fit, difficulty, and whether the section could support it. Advisory only.

    question_evaluationsjudge_batch_runs

  6. The professor reviews it

    Approve, reject or edit. Disagreements with the judges teach the generator and the judges, per subject.

    professor_reviewsreview_outcomestype_instructionsjudge_prompts

  7. A classroom link is made

    Approved questions of one taxonomy are frozen into a set. A link (alias) points students at it.

    question_set_versionsquestion_set_membersquestion_set_aliases

  8. A student practises

    Each answer is scored, and the student's mastery and weak spots move. The next question is picked from those.

    studentstraining_sessionsstudent_attemptsstudent_topic_masterystudent_subtopic_weakness

Inside a question

The questions row keeps its detail as JSON, so every question type can store what it needs without new columns. The type decides what goes into content_json.

FieldWhat it holds
content_jsonThe question as written, including its answer key: options and the right index, the code to read, the hidden tests, the number with its unit and tolerance, the expected formula. Students never see this directly.
spec_jsonWhat was asked for: section, type, difficulty.
generation_attempts_jsonEach try the AI made, and what failed (the retry loop).
validation_report_jsonEvery automatic check: "gradable", the reference solution passes its tests, the number matches its calculation, and so on.
pedagogical_eval_jsonThe four judges' latest verdicts and rationales.
personalization_context_jsonWhich instruction wrote it: the shipped one or a learned one.

Not in the database

Some important pieces are code or files, not tables.

Graders

The seven checking engines (choice, ordering, text, Python tests, units, formulas…) live in the graders/ folder. A course only stores which ones it needs.

Question types

Each type is one code module in app/question_types/: its instruction to the AI, its checks, what students see.

Subjects & catalog

The subject presets and which types each offers are code (app/assessment/catalog.py). A course stores its chosen subject and types.

Original PDFs

Uploaded files sit in data/books/. The database keeps their extracted text.

The AI

The language model is an outside service (OpenRouter). The database keeps what it produced, never the conversation.

Built from the app's own models (app/persistence/models.py, migration 0004) on the feature/courses branch.
